# Architecture

## Layers

```
ui/src/performance/            Svelte pages (one per tab) and their parts
ui/src/lib/ff.svelte.ts        shared page state, polling tied to visible pages
ui/src/lib/api.ts              ff.* and nv.* wrappers around Tauri commands
src-tauri/src/frameforge_cmds.rs   thin commands (ff_*), launch watcher thread
crates/core/src/frameforge/    all logic, no GUI dependencies
```

Commands hold no decisions. Anything that scans hardware, talks to a driver or lists processes runs on Tauri's blocking pool. `FrameForge` (the facade in `service.rs`) is created on first use, so starting Arcadia loads no GPU driver library until the Performance section, or an opted-in automatic feature, needs it.

## Core modules

| Module | Role |
|---|---|
| `service.rs` | `FrameForge` facade: everything the shell calls |
| `hardware.rs`, `hardware_win.rs`, `winsys.rs` | Inventory: CPU, memory, drives, displays, OS, power plans, startup apps, gaming settings |
| `gpu/` | Vendor-neutral GPU model, `VendorAdapter` trait, NVIDIA / AMD / Intel adapters, registry, mocks |
| `ffi/` | Bindings: NVAPI, IGCL, ADLX (feature-gated), PresentMon types |
| `telemetry.rs` | Periodic CPU / memory / GPU samples |
| `presentmon/` | Frame sources: PresentMon Service API, console application (CSV), replay |
| `monitor.rs`, `stats.rs` | Live monitor thread, rolling window, recording, frame statistics |
| `diagnostics.rs` | Deterministic rule engine for "what limits performance" |
| `optimizer/` | Action registry, engine with recorded sessions, history, system-operations trait |
| `processes.rs` | Process list, categories, protection list, library matching, priority rules |
| `nvidia/` | DRS backend, `.nip` reader / writer, setting metadata, snapshots, Profile Inspector fallback |
| `presets.rs` | Arcadia GPU presets (vendor-neutral JSON container) |
| `profiles.rs` | Game profiles, launch lifecycle, benchmark capture glue |
| `benchmark.rs` | Session summary, store, comparison, CSV / JSON export |
| `config.rs` | Settings with schema migration |

## Traits and mocks

Every backend that touches the system sits behind a trait with an in-memory implementation:

| Trait | Real implementation | Mock |
|---|---|---|
| `gpu::BaseEnumerator` | DXGI / registry enumeration | `MockBase` |
| `gpu::VendorAdapter` | NVAPI, ADLX, IGCL | `MockVendor` |
| `optimizer::ops::SystemOps` | Win32 power, registry | `MockOps` |
| `processes::ProcessOps` | Win32 process API | `MockProcs` |
| `nvidia::DrsBackend` / `DrsSession` | `NvapiDrs` | `MockDrs` |
| `presentmon::FrameSource` | service, console app | `ReplaySource` |

Tests build a `FrameForge` from mocks (`FrameForge::with_parts`) and never touch the real system. Two hooks exist for the same purpose: `set_process_list` and `set_source_factory`.

## Data on disk

Everything is under `%LOCALAPPDATA%\Arcadia\FrameForge\`:

| Path | Content |
|---|---|
| `config.json` | Settings (schema-versioned, migrated on load) |
| `history\` | One JSON file per optimiser session |
| `nvidia\backups\` | `.nip` snapshots and their index |
| `presets\` | Arcadia GPU presets |
| `profiles\` | Game profiles |
| `benchmarks\` | Benchmark sessions |
| `cache\` | Disposable data |

Files are written atomically (temporary file, then rename). Ids used as file names are generated by Arcadia and checked against a strict pattern before use, so an id can never escape its folder.

## Automatic features

A watcher thread (`start_watcher`) wakes every three seconds. Until the user turns on automatic profiles or automatic monitoring, each pass only reads `config.json`: it does not list processes and does not create `FrameForge`. Once opted in, it calls `lifecycle_tick`, which closes runs whose game exited and applies profiles to games that just started. Events are kept in memory and emitted to the UI as `ff-lifecycle`.

## Untrusted input

`.nip` files, Arcadia presets and game profile files are treated as hostile: size limits, structure and type checks, id patterns, executable names without paths, numeric ranges against what the driver reports, vendor match. Nothing in a file is ever executed, and a file can only name things Arcadia already knows how to do (driver setting ids, optimiser action ids).
